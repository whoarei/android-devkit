# Android DevKit 版本发布

从当前检出目录识别 Android DevKit 项目，复用仓库中的检查、打包和 CI 流程。开始时读取 [项目发布约定](references/project-release.md) 和仓库当前的 `AGENTS.md`、`README.md`、`.github/workflows/ci.yml`；以实际代码为准，不依赖历史版本号、测试数量或本机路径。

**新版本直接走 GitHub Actions，不需要本地构建。** 本地准备版本与变更说明、执行轻量一致性检查、提交和推送。CI 负责依赖安装、完整回归、编译、打包、签名、产物校验和发布。发布后从 GitHub 获取公开 Release 的版本和下载链接。只有用户明确要求本地构建或打包时，才运行相关本地命令。

## 判断任务范围

- **准备 / 检查发布**：完成版本、变更说明、轻量检查及 CI 配置核对，给出可审阅的结果；不进行本地构建或打包，不推送发布标签。需要远端试构建时，使用已获授权的手动工作流运行，不用发布标签试运行。
- **发布新版本**：在当前对话授权内完成定版、版本修改、提交、推送、标签、CI 跟踪和发布核验。
- **检查 / 修复已有发布**：先读取该标签对应的提交、CI 和 Release 状态，定位失败阶段，再决定恢复方式。
- 创建或编辑这个 skill 本身不触发应用发布。预发布版本须先适配当前只接受稳定版本的检查器和 CI，不能只添加 `-beta` 后缀。

## 确定版本号

核对源码版本、版本号最高的已正式发布稳定版，以及从该发布标签到候选代码的完整差异。差异涵盖拟发布的本地未推送提交，并单独注明拟纳入的未提交改动。用户已明确指定版本号时沿用，并核对版本格式与标签归属。

**用户未指定版本号时，按以下规则直接定版。** 以已正式发布的最高稳定版为基线，按数字比较三个版本段。同一次发布包含多类变更时，取最高升级级别。

- **主版本 `MAJOR`**。从 `1.0.0` 起，破坏现有接口、配置或数据兼容性，移除用户依赖的能力，或提高最低运行要求时，主版本加一，次版本和补丁版本归零。
- **次版本 `MINOR`**。向后兼容地新增功能、扩展现有能力或增加可用的操作流程时，次版本加一，补丁版本归零。基线为 `0.x` 时，不兼容变更也升级次版本并在发布说明中写明影响。进入 `1.0.0` 按用户明确指定的版本执行。
- **补丁版本 `PATCH`**。仅有问题修复、性能与稳定性改进、界面布局或文案微调、例行维护时，补丁版本加一。

例如，以 `0.10.0` 为基线，仅有修复和布局调整时定为 `0.10.1`，新增兼容功能时定为 `0.11.0`。本地版本文件已预填时，仍从已发布的基线计算一次。

目标标签已存在时，先核实对应提交、CI 和 Release 状态，并按已有发布或失败恢复的流程处理。需要发布新代码且自动计算的版本被其他提交占用时，在已选的主次版本下递增补丁号，直至找到可用标签。用户指定版本发生冲突时，报告冲突并保留用户的版本选择。

说明本次主要改动、已知兼容性影响、上一正式版本、确定的版本号和升级理由，然后按用户授权的范围继续。仅要求发布准备时，交付本地准备结果和拟推送的提交与标签。

## 准备发布

1. 确认仓库身份、`origin`、当前分支和工作区；查看本地未推送提交、远端标签和最近正式发布。以最近已发布标签到候选提交的差异编写说明，不能只看最后一个提交。网络或认证失败不能当成“标签不存在”。
2. 将目标稳定版本同步到 `package.json`、`src-tauri/tauri.conf.json`、`src-tauri/Cargo.toml` 的项目条目，以及 `src-tauri/Cargo.lock` 中 `android-devkit` 自身条目。只改本项目版本，不全局替换依赖版本，不顺带升级工具链。同步 README 的版本、下载文件名和本次发布说明。
3. 本地运行现有版本检查，包含将发布的 `vX.Y.Z` 标签，并核对差异与工作流。格式、前端、Clippy、Rust、IPC 类型、隔离浏览器和安装器检查由当前 CI 执行，不在发布前重复安装依赖、编译或重跑整套测试；同一候选代码已有的功能验证可直接引用。真实 SDK / AVD 专项按变更和用户授权决定，不把本地真机当成默认测试目标。
4. 核对 CI 会完整构建 release EXE、NSIS 安装器和便携包，并执行许可清单、安装器内容和更新签名校验。正式签名构建使用 `tauri.release.conf.json`、已有 GitHub Secrets 和 `package-release.ps1 -WithUpdater`；不读取或导出签名私钥到本地。必要的源码变更进入发布提交；二进制、截图、缓存不加入 Git。
5. 正式产物以本次候选提交对应的 CI 结果为准，发布目录应只含本版本预期的八个资产，包括安装包签名和更新清单。正常发版无需清理或迁移本地历史 `artifacts/`，也不使用旧本地产物补包或手工上传。CI 出现旧文件混入时修复其输出隔离，再按失败恢复规则处理。

默认交付两种形式：当前用户安装的 `setup.exe` 和包含程序、许可、构建信息的便携 ZIP。裸 EXE 可作为本地运行入口，不能替代既定便携发行包。

## 提交和发布

1. 展示版本、实际变更、检查结果与限制。只提交本次发布有关的源码和文档；已有用户改动先辨别归属，不 reset、stash 或一并提交未知改动。
2. 记录候选提交 SHA，确认版本一致且工作区没有会改变构建结果的未提交内容。遵守项目分支策略；普通“提交”不等于要求推送和发版。
3. 对已授权的正式发布，推送发布分支，并创建指向该候选 SHA 的新注解标签 `vX.Y.Z` 后精确推送该标签。当前 `v*` 推送会自动公开发布；只准备或只要草稿时不要用标签推送来试运行。
4. 用仓库、工作流、提交 SHA、事件和标签筛选 CI，跟踪确切的标签运行。普通分支 CI 成功不等于发布成功。每次等待不超过 60 秒，持续给出有变化的进度；CI 失败时读取失败步骤并修复原因，不绕过检查手工上传。
5. CI 已负责创建 Release，正常路径不另行调用 `gh release create`，避免重复。出现超时或结果不明时，先重新读取标签、运行及 Release 状态，再重试有必要的步骤。

已有远端标签或 Release 时先核实是否属于同一提交、是否已成功及资产是否齐全。默认不移动标签、不删除 Release、不用 `--clobber` 覆盖资产；源码修复通常使用新版本。已有标签的源码没有变化、只是 CI 基础设施失败时，可重跑原失败运行。明确要求替换已发布版本时，再按该次授权评估和处理。

## 确认发布并汇报

- 确认远端标签解析到记录的候选 SHA，相关 CI 构建与发布任务成功。
- 只读取 GitHub Release 元数据，确认目标版本已公开发布，并取得安装包和便携 ZIP 的实际下载链接。文件内容校验以 CI 结果为准。查询命令见 [项目发布约定](references/project-release.md)。
- 发布成功后只汇报版本号、安装包下载链接和便携 ZIP 下载链接。仍在等待或遇到失败时，说明当前阶段和具体原因。只做准备时，汇报版本、修改摘要、轻量检查结果和待执行的 CI 步骤。
