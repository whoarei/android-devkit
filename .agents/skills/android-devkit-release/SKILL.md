# Android DevKit 版本发布

从当前检出目录识别 Android DevKit 项目，复用仓库中的检查、打包和 CI 流程。开始时读取 [项目发布约定](references/project-release.md) 和仓库当前的 `AGENTS.md`、`README.md`、`.github/workflows/ci.yml`；以实际代码为准，不依赖历史版本号、测试数量或本机路径。

## 判断任务范围

- **准备 / 检查发布**：完成本地版本、变更说明、检查和打包，给出可审阅的结果；不推送发布标签。
- **发布指定版本**：在当前对话授权内完成必要的版本修改、提交、推送、标签、CI 跟踪和发布核验。明确的发布请求已包含这些常规步骤，不重复索要确认。
- **检查 / 修复已有发布**：先读取该标签对应的提交、CI 和 Release 状态，定位失败阶段，再决定恢复方式。
- 创建或编辑这个 skill 本身不触发应用发布。预发布版本须先适配当前只接受稳定版本的检查器和 CI，不能只添加 `-beta` 后缀。

用户只说“发布新版本”等未指定版本号的指令时，按以下顺序准备版本确认：

1. 核对当前版本、最近已发布版本，以及该发布标签到当前候选代码的完整差异，包含本地尚未推送的相关提交；若有计划纳入发布的未提交改动，单独注明其状态。
2. **先向用户列出本次拟发布的主要修改点**，用用户能理解的功能变化、问题修复和兼容性影响概括，不只列提交标题。说明已知的不兼容变更；检查尚未完成或发布范围存在不确定性时如实指出。
3. 在修改摘要之后，给出推荐版本号及简短理由，再明确询问用户选择或确认目标版本；可用时使用 `request_user_input_async`。提问应包含当前 / 上次发布版本、主要修改点和推荐理由，使用户仅阅读提问也能判断版本号，不能只问“发布哪个版本”。

用户未答复期间可继续与版本号无关的检查，但不得改写版本文件、创建发布提交或标签、推送发布标签及发布。等待超时不能当作确认。若答复前候选发布范围发生实质变化，更新修改摘要和版本建议，再按新的范围取得版本确认。用户已在当前请求或前文中明确指定 / 确认版本号时沿用该决定，不重复询问；用户明确授权自行决定版本号时按授权执行并说明选择。

只要求准备时，先完成所有已授权的本地工作；若还需要正式发布授权，在最终可审阅结果中指出将推送的提交和标签。保留当前会话已有授权，不增加重复确认步骤。

## 准备发布

1. 确认仓库身份、`origin`、当前分支和工作区；查看本地未推送提交、远端标签和最近正式发布。以最近已发布标签到候选提交的差异编写说明，不能只看最后一个提交。网络或认证失败不能当成“标签不存在”。
2. 将目标稳定版本同步到 `package.json`、`src-tauri/tauri.conf.json`、`src-tauri/Cargo.toml` 的项目条目，以及 `src-tauri/Cargo.lock` 中 `android-devkit` 自身条目。只改本项目版本，不全局替换依赖版本，不顺带升级工具链。同步 README 的版本、下载文件名和本次发布说明。
3. 运行仓库现有版本检查，包含将发布的 `vX.Y.Z` 标签。按当前 CI 执行格式、前端、Clippy、Rust、IPC 类型和隔离浏览器检查；已在同一候选代码上成功完成的检查可复用证据。忽略的真实 SDK / AVD 测试按变更和授权决定，不把本地真机当成默认测试目标。
4. 完整构建 release EXE 和 NSIS 安装器，再运行发布打包脚本及安装器内容核验。仅 `--no-bundle` 不足以生成当前发布要求的安装包。确保生成的许可清单与声明一致，必要的源码变更进入发布提交；二进制、截图、缓存不加入 Git。
5. 检查发布目录只包含本版本预期的六个资产，防止仓库打包脚本保留的旧版本文件被 `release/*` 上传。目录有旧文件时先核对路径，再移到项目内明确的临时位置，或重新选择干净目录；不要盲目递归清理。

默认交付两种形式：当前用户安装的 `setup.exe` 和包含程序、许可、构建信息的便携 ZIP。裸 EXE 可作为本地运行入口，不能替代既定便携发行包。

## 提交和发布

1. 展示版本、实际变更、检查结果与限制。只提交本次发布有关的源码和文档；已有用户改动先辨别归属，不 reset、stash 或一并提交未知改动。
2. 记录候选提交 SHA，确认版本一致且工作区没有会改变构建结果的未提交内容。遵守项目分支策略；普通“提交”不等于要求推送和发版。
3. 对已授权的正式发布，推送发布分支，并创建指向该候选 SHA 的新注解标签 `vX.Y.Z` 后精确推送该标签。当前 `v*` 推送会自动公开发布；只准备或只要草稿时不要用标签推送来试运行。
4. 用仓库、工作流、提交 SHA、事件和标签筛选 CI，跟踪确切的标签运行。普通分支 CI 成功不等于发布成功。每次等待不超过 60 秒，持续给出有变化的进度；CI 失败时读取失败步骤并修复原因，不绕过检查手工上传。
5. CI 已负责创建 Release，正常路径不另行调用 `gh release create`，避免重复。出现超时或结果不明时，先重新读取标签、运行及 Release 状态，再重试有必要的步骤。

已有远端标签或 Release 时先核实是否属于同一提交、是否已成功及资产是否齐全。默认不移动标签、不删除 Release、不用 `--clobber` 覆盖资产；源码修复通常使用新版本。已有标签的源码没有变化、只是 CI 基础设施失败时，可重跑原失败运行。明确要求替换已发布版本时，再按该次授权评估和处理。

## 核验发布结果

- 确认远端标签解析到记录的候选 SHA，相关 CI 构建与发布任务成功。
- 读取指定版本 Release，核对 `tagName`、公开 / 草稿状态、预发布状态、实际说明及资产名称与大小。不能只检查命令退出码或 Release URL 是否存在。
- 下载这个 Release 的六个资产到新的临时目录，运行下面的只读校验器；将其中便携 ZIP 解压到另一新目录，再带 `--portable` 校验内部 EXE、许可和构建信息。它验证字节和版本一致性，不证明来源可信、代码签名有效或干净机器安装成功。

```powershell
node /absolute/path/to/android-devkit-release/scripts/verify-release-assets.cjs <download-directory> <version> --portable <extracted-zip-directory>
```

命令中的 skill 路径使用当前 `SKILL.md` 所在目录展开；项目和校验脚本都不依赖固定盘符。具体命令见 [项目发布约定](references/project-release.md)。

完成后报告版本、标签 / 提交、Release 链接、安装包 / 便携包下载入口、CI 与下载校验结果，以及尚未完成的实际验证。准备阶段只报告本地产物和剩余步骤；等待中或失败时明确阶段，不宣布发布完成。
